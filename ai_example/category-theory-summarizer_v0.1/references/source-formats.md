# 输入格式要点与已知坑

> 对应步骤 0。`scripts/extract_text.py` 已处理下列大部分情况；本文记录**为什么**这样处理，
> 以及脚本判不了、需要人工判断的情形。

## 支持矩阵

| 扩展名 | 提取器 | 依赖 | 结构保留 | 已知坑 |
| --- | --- | --- | --- | --- |
| `.pdf` | pypdf | `pypdf` | 分页标记 `PAGE i/N` | 扫描件无文本层；公式常成乱序碎片；双栏排版可能串栏 |
| `.docx` | python-docx | `python-docx` | 段落顺序 + 表格（以 `TABLE n` 包裹） | 页眉/页脚、文本框、批注、图表内文字**不提取** |
| `.txt` | 直接读 | 无 | 原样 | 编码不定（见下） |
| `.md` / `.markdown` | 直接读 | 无 | 原样（含 frontmatter、表格、代码围栏） | Markdown 自带换行会被保留，文本偏"稀" |
| `.doc` | **不支持** | — | — | 旧版二进制格式。需先另存为 `.docx` |
| `.rtf` `.pages` `.html` `.htm` | **不支持** | — | — | 需先转存为 `.docx` / `.md` / `.txt` |

## 编码处理

纯文本按此顺序探测，第一个成功的即采用，并在 manifest 中记录：

```
utf-8-sig  →  utf-8  →  gb18030  →  latin-1
```

- `gb18030` 是 `gbk` 的超集，能正确解 GBK 文件（实测通过）
- `latin-1` 永不失败，它是兜底：若落到这一档，**内容很可能已乱码**，须人工确认
- manifest 里 `encoding` 字段会记录实际采用的编码，看到 `latin-1` 要警惕

## 已修复的两个真实缺陷（勿回退）

1. **空页 PDF 被误判为有内容（假阴性）**
   注入的 `===== [x.pdf] PAGE 1/1 =====` 页眉本身就有约 40 字符，导致无文本层的扫描件被判为 `ok`。
   修复：`chars` 只统计**正文**字符（各提取器单独累计 `body_chars`），不含页眉标记。

2. **DOCX 页眉/页脚告警假阳性**
   python-docx 的 `section.header.paragraphs` 即使无文本也非空，导致每次都告警。
   修复：仅在页眉/页脚**确有非空文本**时才告警。

## 门禁脚本同样修过一个假阴性

`check_reports.py` 早期用「全文子串」判定必备章节，结果报告里写一句「本样例缺通俗摘要」
也被判为已具备该章节。修复：改为**按 Markdown 标题**判定。

> 教训固化：任何"某章节是否存在"的检查，都必须按标题/结构判定，不能用全文子串。

## 提取结果异常处理（红线：不静默丢弃）

`extract_text.py` 的三种失败状态与处置方式：

| status | 含义 | 处置 |
| --- | --- | --- |
| `empty` | 提取到 0 个正文字符 | 扫描件 → 需 OCR；或文件确为空 → 与用户确认后剔除 |
| `unsupported` | 格式不支持 | 转格式（`.doc` → `.docx`）后重跑 |
| `error` | 读取异常 | 看 manifest 里的 `traceback` 字段定位 |

**退出码 1 = 有上述任一状态，必须先处置再进步骤 1。** 不允许带着未提取的文件继续。

## 人工仍需判断的情形

脚本判不了、需要在步骤 1「形式化程度」里显式说明的：

- **PDF 公式**：提取出的公式常是碎片化字符流（如 `𝜎! = 𝜎" = ⋯ = 𝜎#$ = 𝜎$`）。报告引用公式时要还原语义，不能照抄碎片。
- **双栏 PDF**：pypdf 按内容流顺序提取，可能左右栏交替。若发现上下文断裂，须人工重排或改按页分段理解。
- **DOCX 图表内文字**：不进正文流。若材料的结论写在图表里，提取器看不到，须人工补。
- **超大材料**：单次不宜超过约 8 万字；超出则按章节分批提取与分批总结。
