# 提示质量画像（Prompt Quality Profile）

> yao-meta-skill Phase 5.7。回答一个具体问题：**本技能的提示行为是否受治理，还是只靠一段好提示碰运气。**

## 需求模型（Need Model）

| 维度 | 本技能的取值 |
| --- | --- |
| 显性需求 | 把一批材料按五步范畴论模型做成结构化总结报告 |
| 隐性需求 | **可复核**——读者要能分辨哪句是材料说的、哪句是模型替它补的。这是原提示词里没写、但决定了整个技能形态的那一条 |
| 场景 | 用户拿讲义/论文/规格说明来要「结构骨架」，通常还要迭代几版才收敛 |
| 用户层级 | practitioner–reviewer：看得懂范畴术语，但会挑刺。**v2 起还要照顾第二类读者**：只懂本领域、不懂范畴论的人——这是「翻译图」要求的来源 |
| 成功标准 | 五件套齐全 + 显式/重构分得开 + 每张图都有翻译图 + 轮次戳与运行目录归档正确 + 门禁通过 |

隐性需求「可复核」是整个包的地基：它解释了为什么要有标注规范、为什么要有置信度星级、为什么门禁把 R1（显式/重构混淆）列为最严重缺陷。若去掉这条，本技能退化成「用范畴术语重写材料」，价值归零。

## 任务族与复杂度

- **任务族**：analytical reasoning（综合 / 结构化抽取）+ execution operation（固定步骤流）。不是 creative generation——本技能不鼓励发挥。
- **复杂度**：**complex**。多输入（四种格式）、多轮迭代、有取舍（重构到什么程度算过界）、产物质量预期高。

复杂度 justify 的是**结构**（references/ + scripts/ + 门禁），不是**入口膨胀**。因此 `SKILL.md` 保持单屏可扫完，细节全部下沉。

## RTF → Skill 映射

| 提示层 | 本技能的落点 | 复核者问题 | 回答 |
| --- | --- | --- | --- |
| Role | 「结构抽取者，不是术语翻译机」；九条红线中的第 2 条即角色约束 | 角色身份是否匹配任务与用户层级？ | 匹配。用户是 reviewer，角色就该是可被挑刺的，而不是权威讲解者。v2 新增「翻译者」子角色：同一套骨架要能用领域语言再说一遍 |

## 质量矩阵自评

| 维度 | 分 | 依据 |
| --- | --- | --- |
| completeness | 5/5 | 输入、输出、流程、红线、门禁、环境全写明；失败路径（提取失败 / 不足以构成范畴）也有处置 |
| clarity | 5/5 | 每步指向具体文件或命令；「迭代 = 从头重写」这类易错点单独成节并写明「在上一轮上贴补丁不算迭代」 |
| consistency | 4/5 | 角色（不编造）、任务（先检索再认输）、格式（信息缺失必须落表）三者一致；v2 的轮次戳/运行目录时间戳分工也不冲突。扣 1 分：门禁尚未覆盖跨轮一致性，与「迭代」的承诺不完全对齐 |
| practicality | 4/5 | 三条命令可直接跑；扣 1 分：依赖 `markitdown` + `pypdf` + `python-docx` 需预装。缺 markitdown 时脚本会报错并给出安装命令，不会静默降级 |
| specificity | 5/5 | 用领域词（对象表/态射表/单子/伴随/Yoneda/信息缺失/翻译图/轮次戳），无「专业地、高质量地」这类空话 |

综合 **23/25**。两处扣分已分别在「下一步迭代方向」和「环境」节显式披露，不藏。

## v2 四条新增要求的落点

| 新增要求 | 落在哪一层 | 怎么被验证 |
| --- | --- | --- |
| MarkItDown 统一转 .md + 源/产物分开归档 | Task：新增步骤 0 与 `convert_markdown.py`；Format：`00_source/` 与 `01_markdown/` 并列 | 转换台账逐文件记录；产物为空/格式不支持即退出码 1；反向用例含 `.doc` 与无文本层 PDF |
| 图节点命名以骨架表为准 | Format + 红线 6 | 门禁逐个比对原图标签与对象表/态射表，点名未命中项；反向用例 `tricky__node_not_in_table` |
| 图后追加通俗化翻译图 | Format + 红线 7 | 门禁断言「有翻译图」与「翻译图确实换了词」；反向用例 `tricky__no_translation` |
| 轮次戳取代每轮时间戳 + 全量归档到时间戳目录 | Format + 红线 4 | 门禁断言轮次戳一致、编号连续、无残留时间戳字段、运行目录名匹配 `\d{8}-\d{6}`；正负两组运行目录用例 |

四条都属于 **Format 层的收紧**，没有改动 Role 与 Task 的骨架——这是有意的：
新要求约束的是「交出什么样」，不是「怎么想」。

## 复核者视角

复核者应能看到需求模型、任务族、复杂度、RTF 映射、质量矩阵五项——本篇全部给出。若缺这些，包可能跑得起来，但提示行为不受治理：换一个人来改，很容易把「显式/重构分开」悄悄删掉而无人察觉。

## 最脆弱的一条

**第 2 条红线（显式与重构必须分开）没有任何自动检查能真正守住它。** 门禁只能数标注出现次数 ≥4，数得出「有标注」，数不出「标注得对」。这是本技能当前最大的治理缺口，任何后续修改都必须优先保护这一条。
