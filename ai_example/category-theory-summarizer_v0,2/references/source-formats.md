# 输入格式、MarkItDown 转换与归档

> 对应步骤 0（`convert_markdown.py`）与步骤 1（`extract_text.py`）。
> 本文记录**为什么**这样处理，以及脚本判不了、需要人工判断的情形。

## 归档结构（红线：源文件与转换文件分开）

```
runs/<YYYYMMDD-HHMMSS>/        # 运行目录，目录名 = 本次运行时间戳
  00_source/                   # 源文件副本，只复制不改动，绝不写入
  01_markdown/                 # 统一后的 .md，后续步骤的唯一输入
  02_reports/                  # R1.md..R4.md + 00_INDEX.md
  manifest_conversion.json     # 逐文件转换台账
```

分开的理由：转换是有损操作。若把转换产物写回源目录，一旦某次转换出错，
原件与产物混杂就无法判断「材料本来就缺这一段」还是「转换丢的」。
保留 `00_source/` 才能回溯核对。

## 转换支持矩阵

| 扩展名 | 处理方式 | 依赖 | 已知坑 |
| --- | --- | --- | --- |
| `.md` `.markdown` `.txt` | 直接复制为 `.md` | 无 | 编码不定（见下） |
| `.pdf` | MarkItDown | `markitdown[pdf]` | 扫描件无文本层；公式常成乱序碎片；双栏可能串栏 |
| `.docx` | MarkItDown（mammoth） | `markitdown[docx]` | 页眉/页脚、文本框、批注可能丢失；表格表头可能为空行 |
| `.pptx` | MarkItDown | `markitdown[pptx]` | 备注页与图表内文字可能丢失 |
| `.xlsx` | MarkItDown | `markitdown[xlsx]` | 多 sheet 会铺平；合并单元格可能拆散 |
| `.html` `.htm` | MarkItDown | `markitdown` | 导航栏/脚本等噪声可能混入 |
| `.doc` | **不支持** | — | 旧版二进制格式。需先另存为 `.docx` |
| `.rtf` `.pages` | **不支持** | — | 需先转存为 `.docx` / `.md` / `.txt` |

实测：DOCX 表格经 MarkItDown 转换后内容完整保留，但表头可能渲染成空行
（`|  |  |  |`），读表时要按数据行对齐，不要按表头对齐。

## 同名冲突处理

`a.pdf` 与 `a.docx` 会转成同一个 `a.md`。脚本检测到目标已存在时，
自动改写为 `a__2.md`、`a__3.md`，**静默覆盖是禁止的**（那属于静默丢弃）。
台账里的 `source_rel` 与 `markdown` 字段一一对应，可回溯。

## 编码处理

转换后按此顺序探测读取，第一个成功的即采用，并在台账中记录：

```
utf-8-sig  →  utf-8  →  gb18030  →  latin-1
```

- `gb18030` 是 `gbk` 的超集，能正确解 GBK 文件（实测通过）
- `latin-1` 永不失败，它是兜底：若落到这一档，**内容很可能已乱码**，须人工确认
- 看到 `latin-1` 要警惕，人工确认后再进步骤 2

## 已修复的真实缺陷（勿回退）

1. **空页 PDF 被误判为有内容（假阴性）**
   注入的 `===== [x.pdf] PAGE 1/1 =====` 页眉本身约 40 字符，导致无文本层的扫描件被判为 `ok`。
   修复：`chars` 只统计**正文**字符（`body_chars`），不含页眉标记。

2. **DOCX 页眉/页脚告警假阳性**
   python-docx 的 `section.header.paragraphs` 即使无文本也非空，导致每次都告警。
   修复：仅在页眉/页脚**确有非空文本**时才告警。

3. **转换产物为空但台账备注为空**
   `scanned_no_text.pdf` 转出 0 字符时，台账里 status=empty 而 warnings 是空的，
   使用者无从判断怎么处置。修复：空产物必须附带可读原因（疑似扫描件/图片页，需 OCR）。

4. **门禁用全文子串判定必备章节（假阴性）**
   报告里写一句「本样例缺通俗摘要」也被判为已具备该章节。修复：改为**按 Markdown 标题**判定。

5. **门禁用全文子串判定交换图（假阴性）**
   判据原为 `"交换图" in text and "→" in text`，正文写「无交换图」而态射表有 `S → ℝ`
   就被判成有图。修复：先定位「交换图」章节标题，只在该章节正文找箭头。

6. **章节区间在第一个子标题处截断（假阴性）**
   「## 3. 交换图」下有「### 3.1 原图」，早期区间结束于下一个任意标题，
   导致父章节被判为空壳。修复：区间结束于**下一个同级或更高级标题**，子标题包含在父章节内。

7. **图的存在靠正文关键词判定（假阴性）**
   判据原本是「章节正文含 `→`」算有原图、「出现『翻译』二字且有一张任意 ≥2 行表」算有翻译图。
   后果：**一份通篇没有一个 Mermaid 图的报告**被判通过，输出还显示「图(译/原)=1/1」——
   「必须出图」和「必须出翻译图」两条要求同时失效。
   修复：图只看 Mermaid 代码块；每个块的类型按它所在的 `###` 子标题判定；
   原图与翻译图须交替出现、数量相等；「翻译对照表」不再能顶替翻译图。
   反向用例 `tricky__prose_only_diagram` 守这条。

> 教训固化（两条）：
> 1. 任何"某结构是否存在"的检查，都必须按标题/结构判定，不能用全文子串；
> 2. 任何检查器解析不到输入时，必须报错，不得报通过。
>
> 第 7 处暴露出这两条还不够，补第三条：**不要用容易匹配的代理信号代替应检查的真实对象**。
> 「有没有图」的真实对象是 Mermaid 代码块，代理信号是正文里的箭头字符。
> 每加一条检查项先问：**我要检查的那个东西，代码里到底有没有真的去读它？**
> 写完必须配一个反向用例证明它真的会拦截——之前的用例全是"改一改现有报告"，
> 于是从来没有人试过"整段删掉"，这条显而易见的路反而一直敞着。

## 转换/提取异常处理（红线：不静默丢弃）

| status | 含义 | 处置 |
| --- | --- | --- |
| `empty` | 转换或提取到 0 个正文字符 | 扫描件 → 需 OCR；或文件确为空 → 与用户确认后剔除 |
| `unsupported` | 格式不支持 | 转格式（`.doc` → `.docx`）后重跑 |
| `error` | 转换/读取异常 | 看台账里的 `warnings` 字段定位 |

**退出码 1 = 有上述任一状态，必须先处置再进步骤 2。** 不允许带着未转出的文件继续。

## 人工仍需判断的情形

脚本判不了、需要在步骤 2「形式化程度」里显式说明的：

- **PDF 公式**：常是碎片化字符流（如 `𝜎! = 𝜎" = ⋯ = 𝜎#$ = 𝜎$`）。报告引用公式时要还原语义，不能照抄碎片。
- **双栏 PDF**：按内容流顺序提取，可能左右栏交替。若发现上下文断裂，须人工重排或改按页分段理解。
- **PPTX/图表内文字**：结论写在图表里时提取不到，须人工补。
- **超大材料**：单次不宜超过约 8 万字；超出则按章节分批转换与分批总结。
